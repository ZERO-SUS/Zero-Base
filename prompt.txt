# ZERO BASE — FULL APPLICATION DEVELOPMENT SPECIFICATION

## ROLE

Act as a senior software architect, full-stack developer, database engineer, cybersecurity engineer, UI/UX designer and DevOps engineer.

Build **Zero Base**, a complete, production-ready, cloud-hosted business management application for a water-tank cleaning service business.

This is a real application that will store actual customer information, service records, payment records, bills and photographs.

Do not build a static demo, fake dashboard, frontend-only prototype or mock database.

Build the actual working application with a secure backend, real database, real cloud file storage, authentication, APIs, deployment configuration and recovery procedures.

Prioritize:
1. Security.
2. Data integrity.
3. Reliability.
4. Correct business logic.
5. Excellent UI/UX.
6. Performance.

---

# 1. TECHNOLOGY STACK

Use the following architecture.

### Frontend
- React
- TypeScript
- Vite
- Tailwind CSS
- Lucide icons

### Hosting
- Cloudflare Pages

### Backend
- Cloudflare Workers
- REST API
- Cloudflare environment bindings and secrets

### Database
- Supabase PostgreSQL

### Authentication
- Supabase Auth
- Private administrator login
- No public registration

### File storage
- Cloudflare R2
- Private R2 bucket
- All customer photographs, bills and uploaded documents must be stored in R2.

### Source control
- Private GitHub repository
- Git-based deployment

IMPORTANT ARCHITECTURE:

Cloudflare Pages serves the frontend.

Cloudflare Workers handles the backend API and secure R2 operations.

Supabase PostgreSQL stores structured business data.

Supabase Auth handles administrator authentication.

Cloudflare R2 stores uploaded files.

Do not use Firebase.

Do not use local databases, local file storage or browser storage as the permanent source of business records.

Use browser storage only for non-sensitive preferences such as theme selection.

All business data must persist in the cloud.

# 7. YEAR-WISE SERVICE HISTORY

This is one of the most important features.

The main Service History page must organize records by the actual date the cleaning happened.

Example:

2026
  November
    16 November — Customer A — ₹1,500
    12 November — Customer B — ₹1,200

  October
    28 October — Customer C — ₹1,000

2025
  December
  November
  October

2024
  December
  November
  October

Requirements:

- Automatically generate years from database records.
- Newest year first.
- Newest month first.
- Newest service date first.
- Expand and collapse years.
- Expand and collapse months.
- Filter by year.
- Filter by month.
- Search by customer.
- Filter by service type.
- Filter by payment status.

CRITICAL DATE RULE:

Use `service_date` for year-wise grouping.

Never use `created_at` or file upload timestamps to determine the service year.

Example:

Actual service date: 20 December 2025.

Record creation date: 5 January 2026.

The service must appear under December 2025.

Keep these fields separate:

- service_date
- created_at
- updated_at
- uploaded_at
- next_due_date

Use Asia/Kolkata as the business timezone.

# 9. PAYMENT MANAGEMENT

- Cash
- UPI

- payment_id
- service_id

- payment_method
- transaction_reference
- payment_date
- notes
- created_at
- created_by
- archived_at

Calculations:

Total amount = Price - Discount.

Amount paid = Sum of valid payments.

Outstanding balance = Total amount - Amount paid.

- Unpaid
- Partially Paid
- Paid
- Refunded

Use reliable database-side validation for financial calculations.

Do not rely only on frontend calculations.

Preserve an audit history when payment records are corrected.

Never silently remove payment records.

# 10. CLOUD FILE STORAGE — CLOUDFLARE R2

All uploaded files must be stored in Cloudflare R2.

Never store uploaded business photographs permanently on the user's device.

Support these upload categories:

- Bill photos
- UPI transaction screenshots
- Before-cleaning photos
- After-cleaning photos
- Tank photos
- Hose photos
- Work-area photos
- Other attachments

Create an attachments database table:

- attachment_id
- service_id
- storage_key
- original_filename
- mime_type
- file_size
- category
- uploaded_at
- uploaded_by
- archived_at

R2 requirements:

- Use a private bucket.
- Use Cloudflare Workers to access R2.
- Use secure authorization checks.
- Generate temporary access links where needed.
- Never expose R2 secret keys in browser code.
- Never store permanent public file URLs.
- Validate actual file types and sizes.
- Generate unique storage keys.
- Handle upload failures.
- Handle database metadata failures.
- Detect orphaned files.
- Provide retry options.
- Do not silently lose uploaded files.

Create a clean folder/key organization strategy using customer IDs, service IDs and unique attachment IDs.

The database should store file metadata and R2 object keys, not image binary data.

# 14. SECURITY

Security is mandatory.

Implement:

- Supabase Auth
- JWT validation in the Worker API
- Role-based authorization
- PostgreSQL Row Level Security
- Private R2 bucket
- Server-side R2 access
- Input validation
- Safe error handling
- Rate limiting
- Request validation
- Secure file uploads
- Audit logs

The Worker must authenticate requests before allowing access to business records or files.

Do not trust frontend-supplied user IDs, roles or permission claims.

Where the Worker accesses Supabase, use a design that preserves authorization and database access policies. Do not expose service-role credentials to the browser.

Never commit:
- API secrets
- Supabase service-role keys
- R2 access keys
- Passwords
- Production environment files

Use environment variables and Cloudflare secrets.

# 15. DATA PROTECTION AND BACKUPS

No system can honestly guarantee zero data loss.

Design Zero Base to minimize the risk and make recovery possible.

Implement:

- Soft deletion.
- Archive and restore.
- Audit logs.
- Safe database transactions.
- Duplicate submission prevention.
- Network failure handling.
- Backup procedures.
- Recovery documentation.

Database and R2 files require separate backup procedures.

A PostgreSQL backup does not automatically contain R2 objects.

Create a documented backup system for:

1. PostgreSQL database.
2. R2 uploaded files.
3. Attachment metadata and storage-key mappings.

Keep backup copies outside the primary production resources.

Use multiple backup generations and retention policies.

Log backup success and failure.

Provide restoration procedures.

Test restoring backups in a separate environment.

Never claim a backup succeeded without verifying it.

# 16. COMPLETE THEME SYSTEM — DARK, LIGHT AND CUSTOM COLOURS

The theme system is an important part of Zero Base.

Build a complete customizable design system.

### Theme modes

Provide three options:

1. Light
2. Dark
3. System Default

The user must be able to switch between Light and Dark instantly.

System Default should follow the device's preferred appearance.

Persist the selected preference so it remains after logout or when opening the application again on another visit.

If appropriate, store the preference in the administrator's profile so it can sync across devices.

### Custom accent colours

Allow the administrator to customize the application's accent colour.

Provide preset palettes such as:

- Ocean Blue
- Royal Blue
- Emerald
- Violet
- Amber
- Crimson
- Slate
- Monochrome

Also provide a custom colour picker.

Allow entering a custom HEX colour.

Example: #2563EB

Validate HEX input before applying it.

### Theme behaviour

Changing the accent colour must update:

- Primary buttons
- Active navigation
- Selected tabs
- Links
- Focus rings
- Selected controls
- Status-independent highlights
- Charts where appropriate

Do not change warning, error and success colours into the accent colour.

Those semantic colours must remain distinguishable.

### Dark theme

Use carefully selected dark surfaces.

Avoid pure black everywhere.

Use different surface levels for:
- Main background
- Sidebar
- Cards
- Modals
- Input fields
- Dropdowns

Maintain readable text contrast.

### Light theme

Use:
- Clean neutral backgrounds
- Clear white surfaces
- Subtle borders
- Appropriate text contrast
- Comfortable spacing

### Design tokens

Build the theme using CSS variables or an equivalent centralized design-token system.

Do not hardcode theme colours independently across individual components.

Create consistent variables for:

- Background
- Surface
- Elevated surface
- Primary text
- Secondary text
- Borders
- Accent
- Accent hover
- Focus
- Success
- Warning
- Error

Ensure every screen, modal, dropdown, form, table and dashboard component supports both light and dark modes.

Avoid flash of the wrong theme during initial loading.

Ensure accessibility and readable contrast for custom colours.
